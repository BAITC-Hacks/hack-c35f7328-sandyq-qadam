Основа интерфейса — работа Адели из `frontend.zip`. Исправления и подключение к модулям команды подготовлены с Ильёй. Не заменяет общий README проекта.

## Запуск

Python 3.11+. Из корня репозитория:

```bash
python -m pip install -r requirements-frontend.txt
python -m streamlit run app/streamlit_app.py
python -m pytest tests/test_frontend.py tests/test_frontend_integration.py -q
```

## Что работает

- Демо из 10 товарных позиций без API-ключей и без модели.
- KPI, фильтры поставщика и риска, карточка SKU, группировка положительных заказов.
- Коды HIGH/MEDIUM/LOW едины с Inventory, на экране переведены на русский.
- Демо-график охватывает полный горизонт товара (14 или 21 день), данные явно обозначены синтетическими.
- Пустые результаты фильтрации и отсутствующие входные файлы показывают понятное сообщение.
- Режим расчёта вызывает модель и Inventory через `src/pipeline.py`. UI не считает запас, риск или заказ.

## Подключение команды

Для «Расчёта по данным» в одной рабочей копии должны присутствовать:

1. `src/forecasting/` Артёма из `dev` (проверялся код в dev-коммите `55dc2cd727cc67a9e3d97588c2aa9f1c8104e41d`).
2. `src/inventory/` Ильи из `feature/inventory`.
3. Эта версия `app/` и `src/pipeline.py`.
4. Подготовленная Артёмом история `data/processed/final_demand.csv` и склад `data/synthetic/inventory.csv`.

SKU склада должны присутствовать в истории. При несовпадении выдаётся ошибка, позиции не отбрасываются незаметно. Идентификаторы читаются строками, включая ведущие нули. Складские поля: sku, stock, incoming, lead_time_days, supplier; необязательно minimum_order_qty (по умолчанию 1), unit_cost (0), product_name, category. Кратность партии и срок поставки — целые числа от 1. История: sku, date, final_demand, anomalies_found, stockout_flag, stockout_adjustment.

Прогноз уже суммарный за `lead_time_days + 7`. Повторного умножения нет. Текущий контракт Артёма не передаёт ошибку прогноза: выбирается существующий fallback Inventory — страховой запас 20% прогноза. ## Проверка

В демо: 10 позиций, 5 HIGH risk, 498 единиц к заказу. Фильтр «Высокий» + Supplier_B оставляет SKU 84997D с заказом 63. Supplier_A + «Средний» даёт понятное пустое состояние.

Локально проверены 9 тестов интерфейса и 12 интеграционных тестов на настоящих функциях Артёма и Inventory с синтетической подготовленной историей; дополнительно 14 прежних тестов Inventory. Без командных модулей интеграционные тесты явно пропускаются. Ручной просмотр экрана выполнен в браузере.

Интеграционный пример: спрос 10 единиц в день, срок поставки 14 дней, пересмотр 7 дней → прогноз 210, резерв 42, остаток 80, в пути 40 → заказать 132. Проверяется изменение результата при изменении истории и товара в пути, JSON-сериализация и показ реального результата в UI.

## Ограничения

Полный запуск на локальной UCI-выгрузке Артёма ещё не проверен. При отсутствии данных нет скрытого перехода на mock. Подготовка данных и stockout correction не выполняются интерфейсом. Модель передаёт суммарный прогноз без дневного ряда: в режиме расчёта показываются настоящая подготовленная история и сумма прогноза, а не выдуманный дневной график. Исторические аномалии не означают текущий риск дефицита. Риск Inventory предполагает своевременное прибытие incoming; MOQ трактуется как кратность. Приложение не отправляет заказы, не ведёт журнал согласования и не подключено к 1С.
